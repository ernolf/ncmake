# Containers and images

| Image | Used by | Purpose |
| --- | --- | --- |
| `ghcr.io/ernolf/ncmake-php:<floor>` | `make build`, anything with `PHP=min`, `php-compat` (one image per minor it checks), the composer half of `deps-audit`, the parser half of `php-audit` | dependencies resolve against the PHP floor, which is what a correct package needs: the declared `min-version`, raised to the floor of the newest end-of-life Nextcloud major when it is lower; `docker.io/library/php:<floor>-cli-alpine` with the extensions a Nextcloud server offers (`php_extensions`), Composer 2, git and unzip, published from `php/Containerfile` of [ncmake-images](https://github.com/ernolf/ncmake-images) for amd64 and arm64 for every PHP minor from that floor to the ceiling of Nextcloud master and rebuilt when one of its inputs changes; pulled like any other image. `localhost/ncmake-php:<floor>` is built on the host from the same Containerfile, which ncmake caches, instead when `php_extensions` in `ncmake.mk` adds an extension the published image lacks, or when no source serves the published one |
| `ghcr.io/ernolf/ncmake-php:<minor>-next`, `ghcr.io/ernolf/ncmake-php:next` | `php-compat`, for a `<php max-version>` above the ceiling of Nextcloud master or with `NEXT=1` | the same Containerfile for every PHP minor above the ceiling of Nextcloud master, built from its release or, before it, from the newest alpha, beta or RC (`docker.io/library/php:<minor>-rc-cli-alpine`), published by ncmake-images for amd64 and arm64; `next` names the newest of those minors, and the label `ncmake.php` the exact PHP, for example `8.6.0RC3`. An extension of `php_extensions` that does not build or does not load on that PHP yet is left out, and the label `ncmake.missing` names it. Once master allows a minor, it moves to `ncmake-php:<minor>` and its `-next` image is no longer built. Nothing is built on the host in its place |
| `ghcr.io/ernolf/ncmake-server:<major>`, `ghcr.io/ernolf/ncmake-server:master` (`install_image`) | `install-test`, `runtime-audit`, `profile` | an installed Nextcloud server: the signed release tarball of the major, or the daily one of master, on `docker.io/library/php:<minor>-apache` with the newest PHP minor the major runs on, installed on SQLite while the image is built, with a fixed admin account and nextcloud/profiler, published from `server/Containerfile` of ncmake-images for amd64 and arm64 for every maintained major and for master. It is a throwaway test server; `install-test`, `runtime-audit` and `profile` publish no port of it |
| `ghcr.io/nextcloud-releases/aio-redis:latest` (`profile_redis_image`) | `profile` | the Redis image of Nextcloud All-in-One, run unchanged and without a password beside the server, whose network it shares; the server keeps its local and distributed cache and its file locking on it, so the profiler sees every cache operation. It publishes no port |
| `ghcr.io/ernolf/ncmake-php:<ceiling>` | `make composer`, `make psalm` | the same image at the newest PHP minor Nextcloud master runs on, a current runtime for the dev tools that moves to a new PHP only once master allows it |
| `ghcr.io/ernolf/ncmake-node:latest` (`node_image`, `lib_node_image`) | every npm run, `consistency-audit`, `changelog-lint`, `php-compat`, `install-test`, `deps-audit`, `php-audit`, `secrets-audit`, `bundle-report`, `build-audit`, `build-verify`, every `lint-*` target | one image for every Node line: Debian slim with git, the CA certificates, the compiler node-gyp needs (python3, make, g++), python3-setuptools for the distutils a node-gyp before 10 imports, the archive and download tools an install script finds in the official Node images (bzip2, xz-utils, unzip, curl, wget, patch, file), and Yarn 1, which the official Node images carry for a build script that calls `yarn` without a `yarn.lock`, published by ncmake-images for amd64 and arm64. Node itself is the official build from nodejs.org, checked against its `SHASUMS256.txt`, kept per line in `node/` of the ncmake cache and mounted read-only at `/usr/local`: for npm the newest LTS line `engines.node` allows that is not end of life (without `engines.node` the newest LTS line), for the analysers the newest LTS line, and `build-verify` and `deps-audit` put the app's line first on PATH for the build steps and the audit. When no source serves the image, `docker.io/library/buildpack-deps:trixie` runs instead, which carries no Yarn 1. A `node_image` or `lib_node_image` set in `ncmake.mk` runs as it is |
| `docker.io/fsfe/reuse` | `make reuse` | the REUSE compliance checker |
| `docker.io/library/php:<version>-cli-alpine` | `make lint-php-syntax` | the plain PHP image, one per version the target checks; `php -l` needs no extension |

`make php-containerfile` prints the Containerfile of the ncmake-php images as cached on this host, with its build arguments `base`, `composer` and `extensions`; it needs no app and changes nothing.

`PHP=min|max` switches the PHP side explicitly. `build` pins `PHP := min`, `psalm` pins `PHP := max`. `RUNTIME=podman|docker|docker-rootless|bare` selects the runtime; it is auto-detected with podman preferred, and `docker` maps the caller's uid and gid so no root-owned files appear in the checkout.

Every Node container mounts `npm/`, `corepack/` and `yarn/` of the per-machine ncmake cache (`${XDG_CACHE_HOME:-~/.cache}/ncmake/`) read-write as the download cache of npm, corepack and yarn, so the tarballs of a lockfile and the package managers corepack fetches are downloaded once per host, and `make build`, `build-verify` and the next app share them; `npm ci` and yarn check every tarball against the `integrity` the lockfile records. Yarn 1, from corepack or the one in `ncmake-node`, keeps its cache in `yarn/` (`YARN_CACHE_FOLDER`), Yarn 2 and later their global cache in `yarn/berry/` (`YARN_GLOBAL_FOLDER`); their project cache stays where the app puts it. `RUNTIME=bare` keeps the npm cache of the host.

Every container runs with `--rm` and `--label ncmake`. Before it starts, its image is pulled again once the last check is older than `IMAGE_CHECK_MIN` minutes (default 1440), and the image that pull superseded is removed right away. Images that a container still uses or another tag still names stay. `images.txt` records each image ncmake used, whether ncmake pulled it or found it on the host, and when it was last used and checked. It is state, not cache, and lives beside the image store it describes: `${XDG_STATE_HOME:-~/.local/state}/ncmake/` for a rootless store (podman run by a user, rootless docker), `/var/lib/ncmake/` for a store of the whole host (podman run by root, rootful docker). For rootful docker run by a member of the docker group, ncmake asks once whether to create `/var/lib/ncmake` with sudo; on no it keeps the record per user, and `make image-setup` asks again. Deleting the cache leaves the record alone.

Which registry serves an image is data, not code: `core/image-sources` in the ncmake repo lists, per image reference prefix, the registries to try in order (for the Docker Official Images ECR Public, then `mirror.gcr.io`, then Docker Hub, whose anonymous pull limit is the strictest). A pull that fails, through a rate limit or otherwise, falls through to the next source. The image is tagged with its reference afterwards, so the host keeps one name whatever served it. The list is cached and refreshed like the Makefile; `IMAGE_SOURCES=<file>` uses a list of one's own instead.

What changes over time about the world outside is data as well: `data/nextcloud-server.json` in the ncmake repo holds the Nextcloud majors (in development on master, newest released, maintained, newest end of life) the PHP range each runs on by its `lib/versioncheck.php` and the PHP extensions each requires by its `composer.json`, `data/node-schedule.json` the Node.js release schedule, `data/appstore.json` the licences, the changelog languages and the deprecated licence names of the App Store, `data/nextcloud-eslint.json` the globals of the released `@nextcloud/eslint-config`, `data/github-runners.json` the self-hosted runner labels the workflows of Nextcloud run on, `data/tool-configs.json` the names of the configuration files each linter and each tool `consistency-audit` looks for reads, as the source of the tool lists them, `data/workflow-scripts.json` the `package.json` scripts each workflow template of `make workflows-install` runs, and `data/tools.json` the newest release of each tool the lint and audit modules fetch, with the sha256 digest its publisher records, `data/gitleaks-rules.json` the rule ids of the gitleaks release `secrets-audit` runs, `data/zizmor-audits.json` the audits of the zizmor release `lint-actions-security` runs, `data/composer-auth.json` the keys of the `auth.json` of composer that hold a credential, and `data/spdx-licenses.json` the licence and exception ids of the SPDX license list, which `consistency-audit` holds the licences of `package.json` and `composer.json` against. A workflow there regenerates them daily from the sources each file names and opens a pull request when a value changes; nothing under `data/` is edited by hand, and `make data-check` there fails when a value of `data/` is written out in the code instead of being read. The core fetches a file into the cache when a value of it is first needed and refreshes it like the analyser libraries, so no run queries those sources itself. Where a file cannot be read, the analyser that needs it says which comparison it left out, and a lint target or `secrets-audit` stops, as it has no release to fetch.

`make image-clean` lists the images of every container CLI on the host with size, last use and status (`ncmake`, `built`, `ncmake-used`, `dangling`, `foreign`, `in use`) and removes the ones picked at the prompt. `OWN=1` picks every image ncmake pulled but not the one it built, `OLD=1` every dangling image and every image ncmake pulled or built unused for `IMAGE_IDLE_MIN` minutes (default 10), `DRY=1` only shows the pick. The flags never pick a foreign image or one in use, and nothing is removed with `-f`. It removes images from the host, so run it only when the user asks for it.

`make cache-clean` lists the per-machine ncmake cache entry by entry, with size, last change and status (`ncmake`, `leftover`, `in use`, `foreign`): the core, developer modules, analyser libraries and registry list of each ref, every Node.js line, the release index of nodejs.org, `npm/`, `corepack/`, `yarn/`, each tool the lint module, `secrets-audit` or `php-audit` fetched into `tools/`, `last-run` and what an interrupted download left. It removes the entries picked at the prompt, by number or `all`; `ALL=1` picks every entry but a foreign one, `DRY=1` only shows the pick. An entry a running ncmake container mounts stays, `all` and `ALL=1` are refused while one runs, and the directory itself goes only once it is empty. The next run fetches a removed entry again, except the developer modules, which come back only with `make dev-init`. It removes files from the host, so run it only when the user asks for it.

Once no ncmake container has run for `IMAGE_IDLE_MIN` minutes (default 10), the images ncmake pulled itself are removed, as `make image-clean OWN=1` does; a PHP floor image it built on the host stays. A detached waiter that each container run starts does this, so a sequence of targets reuses the images in between. `KEEP=1` starts no waiter, for a series of runs that should keep the images; CI (`CI` set) and `RUNTIME=bare` start none either.
