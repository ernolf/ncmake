# Checkout audit module

Ten more analysers, in `mk/audit.mk`, about the checkout rather than the bundle. They share the report core with the bundle analysers, so findings read the same way everywhere.

| Target | Reads | Answers |
| --- | --- | --- |
| `make consistency-audit` | the metadata: `appinfo/info.xml`, `package.json`, `composer.json`, `.nvmrc`, the installed workflows | whether the checkout agrees with itself, and what a release still needs |
| `make build-verify` | the tracked source, rebuilt twice outside the app | whether the build output committed to the checkout comes from that source |
| `make changelog-lint` | `CHANGELOG.md`, `CHANGELOG.<code>.md`, the version in `appinfo/info.xml` | whether the App Store finds this release in the changelog |
| `make php-compat` | the checkout run on the PHP floor and ceiling, `appinfo/info.xml`, the installed packages | whether the app runs on the PHP versions its servers run it on |
| `make install-test` | the staged app, installed on a Nextcloud server per major, and the log of that server | whether the packaged app installs and runs on the servers it declares |
| `make runtime-audit` | the staged app on the same servers, each route, command, job and settings page of the inventory of `php-audit`, and the log per step | whether what the app registers works on a real server |
| `make profile` | the requests of a server without the app, with its previous release and with the staged app, through nextcloud/profiler | what the app costs the requests of a server, and whether that grew since the previous release |
| `make deps-audit` | `composer.lock` and the npm lock file, through the package managers' own audits, and the licence in `appinfo/info.xml` | whether a dependency that ships has a published vulnerability, whether an update can reach the fix, and whether its licence goes with the app's |
| `make php-audit` | the PHP source in `appinfo/`, `lib/` and `templates/`, parsed with nikic/php-parser, `info.xml` and the Composer setup | what the app has (classes, registrations, background jobs, endpoints), and whether the server can load and run it the way the developer manual describes |
| `make secrets-audit` | what ships and every commit of the checkout, through gitleaks | whether a key or a token is in the release or in the history |

`consistency-audit` holds the statements a checkout makes against each other: the version in `appinfo/info.xml` against the ones in `package.json` and `composer.json`, compared as written (a difference names `make version` and the `lint-version` workflow that gates it), the PHP floor in `info.xml` against `composer.json`, every PHP extension that `composer.json` or a package in `composer.lock` requires against the `<lib>` entries in `info.xml`, unless every Nextcloud server has it, the Node version in `package.json` against `.nvmrc` and against the installed workflows, the scripts of `package.json` against the workflows under `.github/workflows/`: a script a workflow runs that `package.json` lacks and an install with another package manager than the one of the lockfile are `[!]` (`workflow-script-missing`, `workflow-package-manager`), a script a template of `make workflows-install` runs while no installed workflow does is `[i]` `script-without-workflow` with the `make workflows-install W=<template>` that adds it, and a watcher or development build under another name than `watch` or `dev` is `[i]` `script-names`. A linter checks one file against a rule and cannot see any of that. The second half is what a release needs and a checkout can be missing: the `<repository>` and `<bugs>` links, a `<nextcloud>` range that names servers that exist, one lockfile rather than two, a licence stated the same way everywhere, a linter a script calls while no configuration for it is in the tree. Metadata only, no build, no install, which makes it useful on a fresh clone and on an app that never heard of ncmake. The majors of nextcloud/server come from `data/nextcloud-server.json`: a `<nextcloud max-version>` above the major in development on master is `[!]`, and where the file cannot be read, the range is not held against the servers that exist. It also asks whether the links of the App Store listing in `info.xml` answer, one `HEAD` each: a dead link (404, 410, a host that does not resolve) and a `<screenshot>` not served as an image are `[!]` (`link-dead`, `screenshot-not-image`); an error or timeout, a permanent redirect with its target, and an `http://` link that answers over `https://` are `[i]` (`link-error`, `link-redirect`, `link-insecure`). A screenshot pinned to a release tag of the app that is not tagged yet is `[i]` `link-pending` while its file is in the working tree. `NO_NETWORK=1` leaves the links unchecked (`link-unchecked`).

`build-verify` answers the other question: it copies the tracked files into a scratch tree outside the app, installs the locked dependencies there, runs the build - twice, the second time in another directory - and compares the result against what the checkout carries. Twice, because one build cannot separate a difference of the source from output that is not reproducible: what both builds wrote byte for byte the same is what this source produces, so a difference against the checkout is the checkout's, while a file the two builds disagree on is named and gets no verdict. With `ARGS=--fresh`, after a `make build` on this working tree, an output the checkout does not commit and that matches the first build on every file name and every byte but build metadata stands in for the second build, which then does not run. Hashed file names are paired by content, so `app-3f9c1a2b.mjs` and `app-8b20de41.mjs` are one file under two names and a reference carrying the hash counts as build metadata rather than a difference; a source map is compared as the map it is, by what it was compiled from. The checkout is only read: nothing is installed into it and the scratch tree is removed again.

`build-verify` is the one analyser that installs and builds, so it needs the network and takes minutes rather than a second, and it needs git and npm where it runs. `ARGS=--once` builds once and states the open question instead of answering it, `ARGS=--build=dist` verifies another output directory.

`changelog-lint` reads the changelogs as the App Store does when a release is published. The store reads `CHANGELOG.md` for English and `CHANGELOG.<code>.md` for each language of its list (`CHANGELOG.de.md`, `CHANGELOG.pt-br.md`), under exactly those names, decodes them as UTF-8 and shows the section whose heading begins with `## 1.2.3`, `## [1.2.3]` or `## v1.2.3` for the version in `info.xml`; a version with a `-`, and a nightly (`ARGS=--nightly`), is read from `## [Unreleased]`. A tagged pre-release is a release of its own, and the lint asks for its own section `## [X.Y.Z-rc.N]`, as `make changelog` writes it; the store shows that section with the stable `X.Y.Z`, below its own, and reads the page of the pre-release from `## [Unreleased]`, which the lint reports with `[i]`. What the store does not find, the release is published without, silently. `[!]` marks a missing `CHANGELOG.md`, a name that differs only in its spelling (with the `git mv` that fixes it), an unknown language code, a file that is not UTF-8 and a missing or empty section; `[i]` a changelog under a name the store never reads. It exits 1 on a `[!]` finding, and `make tag` runs it before the confirmation and refuses on that exit code (`NO_CHANGELOG_LINT=1` tags regardless); it is worth running on its own right after `make changelog`.

`php-compat` runs the checkout on two PHP versions, each in the build image of that minor (`ghcr.io/ernolf/ncmake-php:<minor>`): the floor `make build` resolves against, and the ceiling, the newest PHP minor that the server of `<nextcloud max-version>` runs on, from `lib/versioncheck.php` of its stable branch, or of master for a major without one, as `data/nextcloud-server.json` of ncmake holds it; a higher `<php max-version>` raises it, but no further than the ceiling of master. `PHP=all` adds every minor in between. On each it runs `composer check-platform-reqs --no-dev` and `php -l` over `appinfo/`, `lib/`, `templates/` and `vendor/`. Beside the runs, and without a container of its own, it resolves every `require` and `include` of a shipped PHP file whose path starts at `__DIR__` or `dirname(__FILE__)` against the files `make stage` takes from the checkout; a path that leaves the app, a plain literal (PHP looks that up along `include_path`) and one built at run time are counted, not checked. `[!]` marks a package or the app's `composer.json` that refuses one of those PHP versions, a shipped file that does not parse, a `require` or `include` of a file that does not ship, a `<php max-version>` below the ceiling (a server on a newer PHP refuses to enable the app), a `<php max-version>` above the ceiling of master (a PHP no server runs yet, on which a server would later enable the app unchecked) and a PHP version that could not be checked; `[i]` a deprecation, an extension the build image lacks, a file of a dev package, a check without `vendor/` or `composer.lock`, an include after an `is_file()`, `file_exists()` or `is_readable()` of the same path, one inside a dependency, and one of `vendor/` before `make build` installed it. Run it after `make build`, so `vendor/` holds what ships; the output of each run stays in `build/php-compat/<minor>`. A `<php max-version>` above the ceiling of master runs once more, in `ghcr.io/ernolf/ncmake-php:<minor>-next`, and `NEXT=1` runs the newest PHP ahead of master, `ghcr.io/ernolf/ncmake-php:next`, for any app; the findings of that run are `[i]`, named after the exact PHP (`8.6.0RC3`), and the report says whether that PHP has a release yet. Its output stays in `build/php-compat/next`; `RUNTIME=bare` leaves it out. It needs the network and exits 1 on a `[!]` finding.

`install-test` installs what `make dist` packs on a real server: the stage, copied into `custom_apps` of a container of `ghcr.io/ernolf/ncmake-server`, enabled with `occ app:enable`. The server then answers requests to the login page, the dashboard, the files app, the user and admin settings, the page of the app, the OCS capabilities and WebDAV, as the admin of the image, and `cron.php` runs once. It is a finding when `occ app:enable` fails or the app is not enabled afterwards, when a request is answered with a server error, when `cron.php` fails, and when `nextcloud.log` has an entry of level 3 or higher that names the app, logged for it or with a path in `custom_apps/<app id>/`; an entry of that level that does not name the app is listed as a note. That is the check for a release that ships without a file it requires, a missing `vendor/` for example: it enables without a word and logs an error on every request. Two servers run, the lowest and the highest major of `<nextcloud min-version>` and `max-version` that an image exists for, each on the PHP of its image; images exist for the maintained majors and for master, and declared majors below them are named, not installed. `NC=all` adds the majors in between, `NC="34 master"` runs the ones it names. The server runs on a database `<dependencies><database>` allows: on SQLite, as the image is installed, where the app names none or sqlite among them; where it names pgsql and not sqlite, beside a container of `ghcr.io/nextcloud-releases/aio-postgresql` (`install_pg_image`), whose network it shares, and the server is installed anew on it before the app comes (`[!]` `install-stopped` when that fails); an app that names only mysql or oci is not installed (`[i]` `install-db-untestable`). Where the PHP of the server is above `<php max-version>`, Nextcloud refuses the app; that is `[!]` `install-php-max-below-server`, the app is not fit for that server as it declares itself. The run then raises max-version in the copy of the app to the PHP of the server and goes on, so the finding says whether the code runs on that PHP anyway; where the app does not enable even so, it runs once more on the server image of the PHP of max-version, `ncmake-server:<tag>-php<minor>`, and the finding names what that run found, or that no such image ran. Some apps build on another app, which `info.xml` has no way to name: where an error of the run says a class of a namespace `OCA\<X>` does not exist and no enabled app has that namespace, the app of the App Store whose id that namespace stands for (lower case, or each inner capital as `_`) is fetched in the newest release for the server, kept only when its `<namespace>` matches, and the major runs again with it enabled before the app, up to three times for what those apps need in turn; the list of apps comes from the App Store module (`make dev-init`). What the missing app causes, the failed enable, requests, `cron.php` and log entries that name its classes or tables, is folded into `[i]` `install-needs-app`, which names the app that was fetched or why there is none (`runtime-audit` reports the same as `needs-app`). The containers publish no port and are removed after the run; what each run left stays in `build/install-test/<tag>/`. It needs podman or docker, and an image is about 1.6 GB. `TARBALL=<file|https URL>` installs a release tarball instead of the stage, the one the App Store ships for example: nothing is staged, the id and the majors come from the `appinfo/info.xml` in the tarball, which must hold exactly one directory, and the JSON names `"source": "tarball"` and the file. It runs without a checkout too, `make -f <ncmake Makefile> install-test TARBALL=...`; in the checkout of another app it stops.

`runtime-audit` goes further on the same servers: it runs `make php-audit` first and uses what its inventory lists. Every route is requested once without credentials and once as a user, or as the admin where the route declares neither `NoAdminRequired` nor `PublicPage`, a POST, PUT or PATCH with `{}` as its JSON body; a route parameter is filled from the defaults of the route or from `runtime_params` in `ncmake.mk` (`<name>=<value> ...`), and a route with a parameter left over is not requested. Every command the app adds runs with `--help`, every background job in the namespace of the app once with `occ background-job:execute --force-execute`, then come `occ setupchecks`, the settings pages of the app as the admin, the capabilities, a PROPFIND with `Depth: 1`, and disabling and enabling the app again, all at log level 0; where the staged app is a newer release of one the server ships, `occ upgrade` runs after enabling it. The database, the PHP cap of the app and the apps it needs from the App Store are treated as `install-test` treats them (`[!]` `php-max-below-server`, `server-stopped`; `[i]` `server-db-untestable`, `needs-app`). Each step marks the lines of `nextcloud.log` it wrote. Findings: `enable-failed`, `upgrade-failed`, `route-not-registered` (a route of the inventory that `occ router:list` lacks), `route-server-error`, `controller-not-built`, `route-open` (a route without `PublicPage` that answers 2xx without credentials, `"security": true`), `command-not-registered`, `command-failed`, `job-not-listed`, `job-failed`, `setupcheck-not-listed`, `setupcheck-failed`, `settings-not-loaded`, `settings-failed`, `capabilities-failed`, `dav-failed`, `repair-failed`, and of the log, where the app field, a file or a class of the trace is the app: `log-errors` (level 3 or higher), `log-dirty-reads` (where the first frame outside the database layer is the app), `log-long-transaction`, `log-deadlock`; `[i]` `log-dirty-reads-server` (a query the server builds), `log-deprecations`, `routes-skipped`, `capability-not-listed`. It writes `build/reports/runtime-audit.{txt,json}`, keeps each run in `build/runtime-audit/<tag>/` and exits 0 with findings.

`profile` measures what the app costs a server rather than whether it works: it runs `make php-audit` first, then starts the highest declared major (`NC=all` every one) from `ncmake-server` with nextcloud/profiler enabled, the server in debug mode, which the profiler requires, and its caches on the Redis of `profile_redis_image` beside it, neither publishing a port. Three phases run in the same container: `base` without the app (an app the server ships is disabled), `previous` with the previous release, and `app` with the staged app installed over it as an update would, with `occ upgrade` where the server asks for it. Each phase sends its requests twice to warm up and then `profile_rounds` times (default 5): a set that is not the app's (PROPFIND with `Depth: 1` on the files of the admin and on a folder of 200 files, PUT, GET and DELETE of a file, the dashboard, the OCS capabilities and user; `status.php` is not among them, the profiler records nothing for it), and with the app its GET routes, filled from `runtime_params`, plus the requests `profile_requests` in `ncmake.mk` names (`<VERB> <path> ...`, as the admin). The previous release is the tarball or URL `PREVIOUS` names, or the newest release below this version in the App Store catalogue (`make fetch-apps`), a pre-release only when this version is one; `PREVIOUS=none` leaves the phase out. Every figure is the lowest of the rounds, and a difference counts where both sides reached it in two rounds or more, or where it exceeds the spread of the rounds; times and memory are shown, no finding rests on them. Findings: `queries-added` (with the SQL and the frame of the app in the backtrace; added queries none of which has a frame of the app are `[i]` `queries-shifted`, the server running them in another request), `status-changed`, `query-duplicate`, `query-repeated` (the same query with 5 or more parameter sets), `queries-added-since` (more than with the previous release, `[i]` `queries-shifted-since` where none has a frame of the app), `server-not-run`, `server-stopped`, `enable-failed`, `requests-odd` (`profile_requests` is no list of pairs); `[i]` `server-none`, `queries-shifted`, `queries-shifted-since`, `cache-added`, `previous-none`, `previous-not-enabled`, `routes-skipped`, `routes-not-get`, `profile-unstable`. It writes `build/reports/profile.{txt,json}`, keeps each run in `build/profile/<tag>/` and exits 0 with findings.

`deps-audit` asks the package managers' own audits about what ships, dev dependencies left out: `composer audit --locked --no-dev` in the build image of the PHP floor, and `npm audit --omit=dev`, `pnpm audit --prod`, `yarn npm audit --environment production --recursive` or, for Yarn 1, `yarn audit --groups dependencies`, as the lock file decides, on the Node line the app declares, pnpm and yarn through corepack. Each vulnerable package is one `[!]` finding with its advisories, the highest severity among them and the first released version above the locked one that fixes them all; `vulnerable-dependency` when the declared constraints allow that version, with the update command, `vulnerable-dependency-pinned` when a constraint excludes it, naming the constraint and who declares it. Where the build output carries source maps or `.license` files, an npm package that neither names, and that no package they name requires in the lock file, is `[i]` `vulnerable-dependency-not-bundled` instead, in the lock file but not in the bundle; both can miss a package, so it keeps its advisories. The JSON names the packages they name, and `ARGS=--bundle=<file>` reads them from the JSON of an earlier run of the same release in place of the build output, so a later audit needs no build. composer decides that with `composer why-not`; for npm the ranges come from `package-lock.json` or `yarn.lock`, and `pnpm-lock.yaml` records only those of `package.json`, which the finding says for a package further down. `[i]` marks an abandoned composer package with its replacement (`abandoned-dependency`), an advisory source that did not answer (`audit-unavailable`, nothing of that lock file checked) and dependencies without a lock file (`lock-missing`). Every vulnerability finding carries `"security": true` in the JSON. `NO_ADVISORIES=1` (or `ARGS=--no-advisories`) leaves the vulnerabilities out, for a run whose output is public: no npm audit runs, composer audit keeps only the abandoned packages, the report and the JSON (`"advisories": false`) say nothing about an advisory, and every app gets the same `[i]` `advisories-unchecked` instead. The same packages are held against the licence `appinfo/info.xml` declares, by the licence table `lib/licences.json`, a data file whose examples are tested before an app is judged (`ARGS=--self-test` runs only that, and holds every id of the table against the SPDX licence list, `data/spdx-licenses.json`): `licence-incompatible` for a licence that cannot be combined with the app's (`GPL-2.0-only` in an `AGPL-3.0-or-later` app, GPL or AGPL in an app under MIT or Apache-2.0), `licence-non-free` for `CC-BY-NC-*`, `UNLICENSED` and the like, `licence-missing` for a package without a licence, all `[!]`; `licence-unknown` for a licence that is no SPDX expression or one the table gives no verdict on, and `licence-summary`, the shipped packages grouped by licence, both `[i]`. An `OR` expression passes when one of its licences does. `composer.lock` and `package-lock.json` (lockfile version 2 on) record the licences; for `pnpm-lock.yaml` and `yarn.lock` the analyser walks the lock file from the dependencies of `package.json` and reads each licence from the registry. The report goes to `build/reports/deps-audit.txt` and `.json`, the raw output of the audits to `build/deps-audit`, and the target exits 0 with findings: the gates are the lint-deps and lint-licences workflows of ncmake-workflows. It needs the network for the advisories, the released versions and the licences a lock file does not record; it reads `vendor/` and `node_modules/` not at all, so it runs on a fresh clone, where every production package counts as shipped.

`php-audit` parses every PHP file in `appinfo/`, `lib/` and `templates/` with nikic/php-parser in the build image of the PHP floor (`lib/php-audit.php`, which only states what the source says; nothing of the app runs), and the analyser holds that against `appinfo/info.xml`, the Composer setup and the public API of the server over the majors the app declares. What the server has in which major is data, not code: `data/nextcloud-ocp.json`, the classes, methods and constants of the package `nextcloud/ocp` per major and the major that deprecates each (a method the package declares again with `#[\Override]` counts from the major in which a parent has it), and `data/nextcloud-3rdparty.json`, the packages of `composer.lock` of `nextcloud/3rdparty` per major; a finding that depends on a major names the major the data has. The report starts with an inventory, `"inventory"` in the JSON: the classes, what `Application::register()` registers with `IRegistrationContext`, what `info.xml` names (background jobs, settings, commands, DAV plugins, repair steps, navigation, ...) the background jobs with kind, interval, time sensitivity and whether a timed one is in `info.xml`, and the endpoints, which the report prints as a table: every route of `appinfo/routes.php` (also `resources`, and what `registerRoutes()` is given) and of the route attributes `#[Route]`, `#[FrontpageRoute]` and `#[ApiRoute]`, built the way the route parser of the server builds it, with verb, full path, kind (page, API, OCS, public), controller method, the access attributes and annotations of that method (`NoAdminRequired`, `PublicPage`, `NoCSRFRequired`, `NoTwoFactorRequired`, `UserRateLimit`, `AnonRateLimit`, `BruteForceProtection`, `CORS`; an annotation shows as `@<name>`) and the OpenAPI scope, then the DAV plugins and collections of `info.xml` and the registered capabilities. Which apps may state the root of a route outside OCS is data as well, `data/nextcloud-server.json`. The findings, `[!]` unless marked `[i]`. Class loading: `autoloader-generic` (no `composer/autoload.php`, so the server looks every class up in the file system; the finding names the `composer/composer.json` that changes it), `autoloader-not-optimized` (no `config.optimize-autoloader`), `autoloader-authoritative` (optimized beyond level 1), `autoloader-app-namespace` (`autoload.psr-4` does not map the app namespace to `lib/`), `autoloader-not-shipped` (`composer/autoload.php` requires a `vendor/autoload.php` that is neither committed nor written by the build), `namespace-mismatch` (a class in `lib/` off its PSR-4 path that neither a Composer installation below `lib/` (a directory with `composer/autoload_real.php`) nor a `classmap` or `psr-4` entry of another namespace in a `composer.json` of the app loads) and `psr-0`. Dependencies: `vendor-shadows-server` (a package in `vendor/`, or without an installed `vendor/` in `composer.lock`, that the server ships itself in a declared major) and `[i]` `dev-tools-in-root` (development tools in `require-dev` of the root instead of a `vendor-bin/`). Public API: `private-api` (`OC\` and `OC_` classes, `OC::$server`), `implements-consumable` (a class implements or extends what the API marks `#[Consumable]`), `ocp-missing` (a class, method or constant of the public API, or a method of it the app overrides, that a declared major no longer has), `ocp-since-above-min` (one the oldest declared majors do not have yet), `ocp-removed-soon` (a deprecated one Nextcloud master no longer has) and `[i]` `ocp-deprecated` (a deprecated one, with the replacement the deprecation names); `legacy-hook` (a listener on a legacy hook: `OCP\Util::connectHook()`, `OC_Hook::connect()` or `listen()` on a hook scope, `[i]` unless a declared major removed the hook or the oldest one deprecates `connectHook()`, each place with the event that replaces it from `data/nextcloud-hooks.json`, read from the upgrade notes of the developer manual; `ocp-deprecated` leaves these calls to it). Templates: `template-inline-script` (a `<script>` with content and neither a source nor the nonce of the response, or an `on*=` attribute, which the Content Security Policy of the server does not run) and `[i]` `template-inline-style` (a `<style>` with content or a `style=` attribute, which the default policy allows). Registrations: `info-xml-class-missing` and `info-xml-class-wrong-type` (a class `info.xml` names is not there, or is not what the server expects in that place), `setup-check-wrong-type`, `repair-expensive-step` (`IRepairStepExpensive` outside `<post-migration>`) and `install-php` (`appinfo/install.php`, `appinfo/update.php`). Performance: `dav-without-preload` (a DAV plugin on `propFind` without `preloadCollection`), `display-name-lookup` (`IUserManager::get()` only for the display name), `boot-listener` (a listener or a service query in `boot()`), `[i]` `transaction-manual` and `[i]` `job-time-sensitivity` (a timed job that does not say whether it is time sensitive). Platform: `[i]` `time-direct` (`time()`, `new DateTime()` in `lib/`), `[i]` `config-without-lexicon` and `http-client-direct` (curl, Guzzle or a stream to a URL past `OCP\Http\Client\IClientService`), which carries `"security": true` in the JSON. Endpoints: `route-target-missing` (a route names a controller class or method that is missing or not public), `route-duplicate` (one verb and path, or one route name, declared twice), `route-unreferenced` (a route outside OCS that nothing in the app calls: no route name or path in the PHP source, the templates, the frontend source in `src/` or else `js/`, where a text joined to a value before it, `${base}/recipes`, counts as the end of a path, or the navigation), `[i]` `cors-unreferenced` (the same for a route whose method has `CORS` or that answers OPTIONS, which is there for clients outside the app), `[i]` `ocs-unreferenced` (the same for OCS), `frontend-url-without-route` (the frontend or a template builds a URL below `/apps/<id>/` that no route matches), `[i]` `controller-method-unrouted` (a public controller method no route reaches), `csrf-off-state-changing` (`NoCSRFRequired` on a route outside OCS for POST, PUT, PATCH or DELETE), `[i]` `public-without-rate-limit` (`PublicPage` with neither `AnonRateLimit` nor `BruteForceProtection`), `[i]` `annotations-only` (access declared by docblock annotation where every declared major has the attribute), `openapi-drift` (an OCS route that is not in `openapi*.json`, or an operation there that no route provides; a route scoped `ignore` and one for OPTIONS are left out), `[i]` `openapi-missing` (OCS routes and no `openapi.json`) and `[i]` `routes-unreadable` (routes that are no constants in the source: the inventory lacks them, and the findings that need the full list are left out); `csrf-off-state-changing`, `public-without-rate-limit` and `annotations-only` carry `"security": true` as well. Migrations: the steps of `changeSchema()` in `lib/Migration/`, in the order the server runs them, are held against the checks `OC\DB\MigrationService` makes in each declared major, which `data/nextcloud-server.json` has per major (up to 32 only where `<dependencies><database>` is missing or names `oci`): `migration-name-length` (a table, column, index, foreign key or primary key name longer than the server allows, the default table prefix counted), `migration-bool-notnull` (a NotNull boolean column), `migration-notnull-empty-default` (a NotNull column added to an existing table with `''` as its default), `migration-string-length` (a string column longer than 4000), `migration-name-collision` (one index or foreign key name on two tables), `migration-class-name` (a file without the class the server loads from its name, or the reserved version `0`) and `[i]` `migration-not-checked` (a major ncmake has no checks for, or a name or type that is no constant). Each finding names the majors it holds for; a server stops the install or the update there. The routes are read, not requested: whether an endpoint answers is not asked here. A class is judged by what it extends only where all of that is a class of the app, of the public API or of PHP; an interval given as a class constant is not resolved and stays empty; a class of another app is not counted as private API. A file that does not parse is named in the report and left out of the audit. The parser is the release `data/tools.json` names, the tarball of the commit Packagist records for it, kept in `tools/` of the ncmake cache and mounted read-only into the container: nothing is installed into the app, and no `composer.json` or `composer.lock` changes. The report goes to `build/reports/php-audit.txt` and `.json`, what the PHP half read to `build/php-audit`, and the target exits 0 with findings and 2 when the run could not be carried out. It needs the network once per machine, for the parser.

`secrets-audit` runs gitleaks with `--redact` in two scopes: what ships (`SCOPE=shipped`: the files `make stage` takes from the checkout, copied aside, or the tarball `TARBALL=<file>` names) and the history (`SCOPE=history`: every commit, or the git log range `COMMITS=<range>`, which may take several words such as `"--all --not <commit>..."`; for an app below the top of its repository only the commits that touch its directory); `SCOPE=all` is the default. Next to the gitleaks rules it names a file by its name: `*.key`, `id_rsa` and its siblings, a `*.pem` with a private key block, `*.p12`, `*.pfx`, an `.env` file (not `.env.example` and the like), the `auth.json` of composer with a credential under one of the keys `data/composer-auth.json` names (without that file the `[i]` finding `composer-auth-unchecked` says the check is left out) and an `.npmrc` with a token. Files public by design are never reported: `.ncmake/certificate.crt`, and `appinfo/signature.json` and the older `appinfo/checksum.json` where their content is what such a file holds (in the history as of each commit); the `[i]` finding `public-files` counts the matches left out. An `appinfo/signature.json` that is no valid JSON cannot be told from a signature by its content: only the matches of `generic-api-key` and `sourcegraph-access-token` are left out in it, and the `[i]` finding `signature-invalid` names it. A private key block without a base64 run of 64 characters in it is the template of a library that writes keys, and no match. In a generated file (`*.map`, `*.min.js`, `*.min.css`, `*.chunk.js`, `*.chunk.mjs`, `.php-cs-fixer.cache`, `.phpunit.result.cache`, `.eslintcache`, a page of built documentation `assets/js/<name>.<8 hex digits>.js`, or below a directory `.gitignore` takes for build output) a match of `generic-api-key`, or of `sourcegraph-access-token` on a line without an `sgp_` token, is counted in the `[i]` finding `generated-files` instead, in a page of built documentation also one of `curl-auth-user` and `curl-auth-header`; every other rule stays `[!]` there. A value that is no secret by its form, its key or its file is counted in the `[i]` finding `not-secrets`: the name of a constant, a run of the alphabet, a property access in code, a hash under a key that says so (`hash`, `sha256`, `integrity`, `fingerprint`, ...), the checksum of a file under the file's name, the nonce of a WebSocket handshake, the text of an HTML element after an attribute that holds the word, a Stripe test key and a match in a translation under `l10n/`. Test data (below `test/`, `tests/`, `fixtures/`, `__fixtures__/`, `testdata/` or a source set `src/<name>Test/`, a `*.test.*`, `*.spec.*`, `*.golden.*`, `*.mock.*`, `*Test.php` or `*_test.go`), the report of a test run (`newman/`, a Postman collection by its name or the schema it names) and example code (below `example/`, `examples/`, `example-<name>/` or a `demo/` of a vendor package) are counted in the `[i]` finding `samples`; a private key and a GitHub token stay `[!]` there, as a real one ends up in a test as easily. `ARGS=--self-test` checks that those rule ids are rules of gitleaks, `data/gitleaks-rules.json`, and that each of these tables judges its examples and counter-examples as it should. A match whose value is a placeholder of `lib/secrets-placeholders.json` (one regular expression per entry, tested against the value and for a `user:password` pair against the password as well: `admin:admin`, `YOUR_PASSWORD`, `$PASS`, `${NC_PASS:-admin}`, `${{ secrets.TOKEN }}`, `<password>`, `app-password`, a value cut short with `...` and the like) is counted in the `[i]` finding `placeholders`; a placeholder found later is added to that file, and `ARGS=--placeholders=<file>` reads another one. `secret-shipped` and `secret-in-history` are `[!]`, carry `"security": true` and a fingerprint, and never show the secret; `ARGS=--details` names every commit a file found by its name was added in and every file whose matches are counted; `ARGS=--reveal` shows the line of each finding on the terminal only, never in the JSON, and is refused where `CI` is set. `.gitleaks.toml` and `.gitleaksignore` of the repository apply. `"rules"` in the JSON is a sha256 over the gitleaks version, the analyser, the keys of `auth.json` it checks, the placeholders and those two files, so a tool that keeps a history result and later scans only `COMMITS="--all --not <tips>"` knows when to scan in full again. `make secrets-ignore` runs `secrets-audit` with the same options, lists its findings numbered, asks which are false positives (number, range or `all`) and why, and appends each one's fingerprint under a comment with rule, file, commit and reason to `.gitleaksignore`; `REASON=<text>` gives the reason up front, without a terminal it only lists, and `COMMIT=1`/`PR=1` commit it on the branch `ncmake/secrets/ignore`. In an app set up for REUSE a new `.gitleaksignore` starts with the copyright and licence `REUSE.toml` states for itself, so `make reuse` stays green. `make tag` checks what ships before its confirmation and `make dist` the staged tree before it packs it, through the core's `ship_check`, and both stop on `secret-shipped` (`NO_SECRETS_AUDIT=1` goes on). gitleaks is the binary of the GitHub release `data/tools.json` names, checked against the digest GitHub publishes for it, kept in `tools/` of the ncmake cache and fetched by the lint module, so `make dev-init` brings what it needs. It exits 1 on a `[!]` finding and reads no network.

An `<id>` in `appinfo/info.xml` that is no valid app id is a finding of `consistency-audit` alone; every other target that needs the id stops with `SKIPPED:` and names it. `install-test` and `runtime-audit` stop the same way where a build output that ships is missing, so only `make build` reports a failed build. A failure several targets see is reported once, through `"covers"` in the JSON: `install-enable-failed` covers `enable-failed` of `runtime-audit`, `install-php-max-below-server` covers `php-max-below-server` of `php-compat` and of `runtime-audit`, and that of `runtime-audit` the one of `php-compat`.

Like the bundle analysers, each takes `ARGS=--json` and `JSON=<file>`. `make help-consistency-audit`, `make help-build-verify`, `make help-changelog-lint`, `make help-php-compat`, `make help-install-test`, `make help-runtime-audit`, `make help-profile`, `make help-deps-audit`, `make help-php-audit` and `make help-secrets-audit` list every option.
