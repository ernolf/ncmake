# Bundle analysis module

Two analysers on one set of measurements, for an app with a frontend. Neither builds, installs nor touches dependencies, and neither writes anything into the app: no configuration to add, no file to commit, no file to ignore.

| Target | Reads | Answers |
| --- | --- | --- |
| `make bundle-report` | the built directory (default `js/`) | what a browser downloads when a page of this app opens, and which packages those bytes are |
| `make build-audit` | the checkout: bundler config, `package.json`, `src/` | why the bundle is the size it is, priced in the bytes the build delivers |

`bundle-report` counts every file that no other file in the built directory imports as an entry, follows the static import graph to its closure, and adds the stylesheet named after that entry with everything it `@import`s, because entry plus stylesheet is the pairing the app makes in PHP with `addScript` and `addStyle`. Each file is compressed on its own, never concatenated, since each is its own HTTP response. Where the build ships source maps, the delivered bytes are charged back to the modules they came from, so the report names the packages the bundle is actually made of, for the page and apart from it for its lazy chunks. What no mapping covers goes to the owner its code shows: the glue of the bundler, a file of a neighbouring package, of the app, or of the bundler and its plugins; what none of them owns is an `unattributed` finding with file and byte offset. Without maps the file sizes still hold, and the per-package breakdown holds only what the code shows by itself.

`build-audit` reads the half that never ships and prices what it finds there through the same maps, so a statement about how this app imports something comes with what that costs here. It names only what the app itself can change: the toolchain the checkout is built with, each bundler package with the range `package.json` declares and the version the lock file resolves (`toolchain.declared` and `toolchain.resolved` in the JSON), whether the build emits source maps, a page that arrives as one chunk, every package the source imports by its root together with what the build delivers of that package, and moment or a set of statically bound date-fns locales where the source is what pulls them in, and `[i]` `frontend-global`: a global the server sets for the old frontend, `OC.*`, `t()` or `n()` neither imported nor declared, read in `src/` where an `@nextcloud` package has the function or the server marks it deprecated, with the package, the deprecation and the last major that has it, from `data/nextcloud-frontend.json`, read from `core/src/OC/index.js` and `core/src/globals.js` of each stable branch. Where node_modules is installed, the `frameworks` finding names what the delivered packages are written against, a package one of them requires as a non-optional peer, such as Vue 2 or Vue 3 or React, with its installed version and its delivered packages, and every other delivered library with its version; the JSON carries them as `frameworks` and `libraries`. A known toolchain defect that leaves the source maps short of what the build delivers, listed in `lib/build-defects.json` of ncmake, is reported as `[i]` where the lock file holds an affected version and the build shows the symptom; the frameworks and libraries then come from the `.license` files beside the chunks. `make build-audit PROVE=1` builds a throwaway copy with the versions that fix it and says fixed, not fixed or that the copy does not build; it needs the network, and the checkout is not changed. What the bundler or a library decides on its own is measured and tabled under `--details` instead of dressed up as a verdict.

Both mark findings `[!]` worth changing, `[i]` worth knowing, `[ok]` nothing found, and each finding says what it is derived from. `ARGS="--details"` adds the tables behind them, `ARGS=--json` emits the whole result for a script, and `JSON=<file>` writes that result to a file from the same run that prints the report. A finding of the JSON that reports the same cause as a finding of another target, such as the version drift `consistency-audit` and `lint-version` both name, lists that one in `covers`, as `<target>` or `<target>/<id>`. `make help-bundle-report` and `make help-build-audit` list every option.

The analysers are dependency-free ESM files that share their measuring core, so both count the same way. They are fetched into the per-machine ncmake cache on first use, on the same TTL and ETag terms as the modules, and mounted read-only into the throwaway Node container, so the host needs no Node. The fetch happens only when one of the two targets is on the command line, so no other target in any app pays for it.
